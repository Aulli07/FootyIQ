# Real-World Football Stats Schema Sketch

This app currently has two shapes:

- a legacy, UI-friendly nested shape in `app/data/stats/`
- an API-Football-style normalized shape generated by `app/data/stats/api-football-utils.js`

For a real app, the canonical model should be normalized first, then rendered into UI-friendly views.

## Canonical entities

### Player

Stores identity and profile data.

```ts
type Player = {
  id: string;
  fullName: string;
  slug: string;
  nationality?: string;
  dateOfBirth?: string;
  heightCm?: number;
  preferredFoot?: "left" | "right" | "both";
  primaryPosition?: string;
  imageUrl?: string;
};
```

### Club

```ts
type Club = {
  id: string;
  name: string;
  leagueId?: string;
  country?: string;
  logoUrl?: string;
};
```

### Competition

```ts
type Competition = {
  id: string;
  name: string;
  country?: string;
  tier?: number;
};
```

### Season

```ts
type Season = {
  id: string;
  label: string; // e.g. "23/24"
  startYear: number;
  endYear: number;
};
```

### Player season stats

One row per player per season per competition scope.

type PlayerSeasonStats = {

### Player match stats

Use this only if you need match-level analytics.

```ts
type PlayerMatchStats = {

  clubId: string;

```

## Recommended storage model

Keep these separate:

- `players`
- `clubs`
- `competitions`
- `seasons`
- `player_season_stats`
- `player_match_stats` when needed

This avoids duplicating the same player profile inside every season object.

## What your current legacy shape becomes

Current nested data like:

- player -> seasons -> competitions -> stats

should be transformed into:

- one player record
- many season records
- many competition records
- many player season stat rows

## How to use legacy data safely

Use legacy objects as:

- seed fixtures during development
- fallback data when an API is unavailable
- migration input for importing into the canonical schema

Do not use legacy objects as the database source of truth.

## Migration rule of thumb

If the value answers "what happened in football?", store it in canonical rows.

If the value answers "how should the UI show it?", compute it in a selector or adapter.

## Practical mapping from the current app

- `app/data/stats/forwards/*.js` -> legacy seed input
- `app/data/stats/api-football-utils.js` -> adapter/transformation layer
- `app/types/stats.ts` -> canonical app-facing types
- comparison and stat views -> read from normalized stats, then aggregate for display

## Best next step

Define the canonical TypeScript types first, then write one adapter that converts the current legacy stats into those rows.
